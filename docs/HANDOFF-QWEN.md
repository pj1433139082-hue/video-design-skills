# 给千问办公：视频技能流程优化交接

## 用户明确要求

2026-10-15：先建立公开仓库，由千问办公继续实施。用户已经用这套技能产出多条视频，流程仍需优化；考虑执行消耗，本次只建仓与移交。

## 本次已经做的事

- 导入 remotion-consult、remotion-build、remotion-shared 的项目级现有基线。
- 收录共享动效源码、类别模板、参考规范与已有评估定义。
- 将构建指南中的个人 Chrome 绝对路径替换为示例路径。
- 没有改写已安装技能，没有切换同步源，没有重跑视频制作。

## 实施原则

1. 先分析现有实际产出与反复耗时环节，保留已被使用验证的能力；不要因为新建仓库就重写整套流程。
2. 用户报告的成功案例、文件存在、实际运行证据、视觉验收分别记录，不相互替代。
3. 每次优化一个明确问题，说明减少了什么重复工作、有哪些影响，并验证与已有路径兼容。
4. 在本仓库修改、验证；不要自动覆盖维护者各客户端正在使用的技能，也不要擅自运行全量同步。
5. 控制执行消耗：先做静态核查和小范围样张，只有必要时才做完整渲染。

## 建议优先核对的事项

以下是待核查项，不表示每项都已复现为缺陷。

### P0：流程一致性与减少重复

- consult 的共享库查找顺序与 shared 的全局源优先约定不一致，确定一个可移植且统一的规则。
- 已有 DESIGN.md / 已确认风格 / 风格样张通过后，核对 consult 与 build 是否仍重复提问；设计一个沿用已有决策的最短路径。
- consult 的样张需要执行渲染，而全片交给 build，核对样张实现、复用和交接归属，避免相同场景做两遍。
- 流程里含“唯一事实源”声明与重复阈值，核对字幕质量阈值等是否真正只有一处维护。

### P1：依赖和公开使用

- 盘点工作台、资料库、其他设计技能、shotcraft 与 scripts/media 依赖，分类为必需、可选、仅维护者本地。
- 整理媒体脚本接口及可公开部分；不要把含密钥、账号配置或业务素材的整目录直接搬进来。
- 核对现有描述与实现，例如字幕是否对所有视频类别都必须作为唯一时间轴，口播与无口播路径如何区分。
- 明确当前支持的渲染后端与运行环境；库/API 用法以对应版本的官方文档为准。
- 补第三方来源与许可清单，再决定仓库自身适用的许可证。

### P2：回归与交付

- 请维护者从已有产出中选择可公开的代表案例，取得素材与文案后再收录；不要编造案例或私自公开历史视频。
- 将现有 eval 定义中依赖工作台输入的部分改为明确 fixture 或可替换输入。
- 优先选择一个短案例覆盖 DESIGN → 字幕/配音 → 场景 → 抽帧/样张 → 成片交接；是否完整渲染由改动范围决定。
- 记录实际执行的命令、结果、产物与待确认事项，未运行的检查不能写通过。

## 建议交付

先给出“现有流程图 + 重复步骤清单 + 本轮最小修改范围”，随后分批实施；每批附改动理由、验证证据和对原流程的影响。以已经产出视频的工作流为基线持续改进，不把建仓误当成重新立项。
